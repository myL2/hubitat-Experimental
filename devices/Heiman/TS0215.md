# Heiman 4-button security remote (Tuya TS0215) — arm / disarm / home / SOS

Findings from pairing and testing one unit on Hubitat (C-8 Pro, platform 2.5.2) on 2026-10-03/04.
Hubitat device: **260 "Heiman 4btn remote"**.

## Device

| | |
|---|---|
| Brand | Heiman (Tuya OEM; same hardware sold as Smart9 S9ZGBRC01) |
| Zigbee model / manufacturer | `TS0215` / `_TYZB01_qm6djpta` |
| Firmware | application `0x46` (`firmwareMT 120B-4887-00000046`) |
| Power | battery (CR2032); sleepy end device |
| Endpoints | `01` only |
| In clusters | `0000, 0001, 0003, 0020, 0500, 0B05` |
| Out clusters | `0003, 0019` (OTA), `0501` (IAS ACE client) |

Buttons: 🔒 lock, 🔓 unlock, 🏠 home, 🆘 SOS.

## Driver

myL2 **"Tuya Zigbee Security Remote"** (`drivers/Tuya/TuyaZigbeeSecurityRemote.groovy`). No built-in or
installed driver supported it; the device joined as a generic *Device*. With the driver's fingerprint the hub
selects it at pairing.

| Button | Zigbee (cluster 0x0501) | Driver event |
|---|---|---|
| 🔒 lock | Arm (cmd `00`), arm mode `03` (all zones) | `pushed 1`, `action armAway` |
| 🔓 unlock | Arm (cmd `00`), arm mode `00` (disarm) | `pushed 2`, `action disarm` |
| 🏠 home | Arm (cmd `00`), arm mode `01` (day/home zones) | `pushed 3`, `action armHome` |
| 🆘 SOS | Emergency (cmd `02`), no payload | `pushed 4`, `action sos` |

Arm payload: arm mode (enum8), arm/disarm code (empty string `00`), zone id `FF`.
Option *Control Hubitat Safety Monitor* sets HSM from buttons 1–3.

Setup: change the type, click **Configure**, then press a button immediately (the remote only listens right
after a press). Configure writes the hub as IAS CIE, answers the enrol request, binds `0000, 0001, 0500, 0501`
(as Zigbee2MQTT does) and configures battery reporting.

## Findings

- **Battery** `0x0001:0x0021` is in half-percent units (`C8` = 100 %); the generic driver showed 200 %.
  Voltage `0x0020` = `1E` (3.0 V). Reported about every 2 h and after each rejoin.
- **Every press is sent 3 times, ~1.6 s apart, then the remote re-announces (ZDO device announce, same network
  address) about 2 s later**, followed by a node descriptor request ~10 s later.
  - Not fixed by answering the commands (Arm Response / Default Response), by IAS enrolment, or by binding the
    clusters. A matching reply needs the request's ZCL sequence number, which Hubitat does not pass to drivers.
  - Zigbee2MQTT users see 2–3 copies too; its converters drop duplicates by sequence number.
  - Unconfirmed alternative cause: the remote's parent router dropping messages for sleepy end devices (APS acks
    not delivered), which would also explain the rejoin. Not tested next to the hub.
  - The driver ignores repeats of the same command within 2.5 s, so each press is one event.
- **The remote is busy for ~5.5 s after a press** (repeats + rejoin). A second press inside that window is lost
  or delivered only after the rejoin. Rules should not rely on quick button sequences.
- The enrol request (`0x0500` cmd `01`, zone type `0x010F`) is also repeated at pairing until answered.
